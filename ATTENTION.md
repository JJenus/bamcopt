# Website and account-app review items

The public pages use conservative, general information where business details were not supplied. Review these items before a public launch.

- **Legal review:** `/legal/privacy` and `/legal/terms` contain standard baseline wording, not jurisdiction-specific legal advice. Confirm the registered operator, address, eligibility, governing law, complaints/ombudsman channels, financial regulatory disclosures, retention periods, lawful bases, cross-border safeguards, and applicable consumer rights. No license, deposit insurance, or investment guarantee has been asserted.
- **Public configuration:** Set the `NUXT_PUBLIC_*` variables documented in `docs/public-site.md`. Defaults preserve the Bancopt name/phone and assume `support@bancopt.com` and `https://www.bancopt.com`. Verify that the mailbox is monitored and the phone is correct. Legal entity defaults to Bancopt; business address is intentionally blank. Update `NUXT_PUBLIC_LEGAL_UPDATED` when policies change.
- **Investment availability:** No investment execution/product exists in this app. `/investment` is an enquiry/information page only. Replace with approved offering details and disclosures only if a real service is introduced.
- **Product terms:** Confirm supported destinations/currencies, fees, processing times, limits, eligibility, and funding reconciliation procedures. Pages intentionally avoid fixed rates, completion-time promises, invented metrics, reviews, or corporate-banking claims.
- **Support:** Contact uses real `mailto:` and `tel:` links, not a pretend submission form. No delivery or response-time promise is made. A ticket/contact endpoint and newsletter service are not included.
- **Privacy providers:** Public and authentication layouts no longer automatically load chat widgets. Existing protected layouts/integrations are out of scope. Audit all hosting, email, upload, font, and any enabled chat providers; add any required consent mechanism before enabling non-essential tracking.
- **Receipt privacy:** Transaction references open existing public receipts. Treat references as confidential. Review the existing receipt API's exposed fields and abuse protection separately; this redesign does not alter financial APIs.
- **Authentication:** Existing account/session and backend verification behavior is preserved. Registration policy agreement is enforced by the public form but is not stored as a versioned consent record by the backend. Add server-side evidence/version tracking if required.
- **UI scope:** The public site, `/app`, and `/admin` now have redesigned active screens. The UI passes preserved financial behavior; the subsequent funding follow-up adds explicit Credit/Debit corrections, a dedicated reversal action and currency checks (see `docs/funding-operations.md`). Existing transactional email templates retain their legacy branding and `APP_URL` setting; align these separately if rebranding the entire service.
- **Environment example:** `.env.example` was restored at the user's request and includes the public-site variables plus the optional `NUXT_BUILD_DIR` override. Replace example values in a private environment file; do not commit real credentials.

## Account-app follow-up items

- **External destinations:** Existing PayPal/Skrill/MB Way/bank destination choices are preserved as account-ledger entries, not advertised as actual provider integrations. The backend currently records successful account-ledger transfers as completed without an external settlement connector. Confirm the real operational processing and delivery semantics before using these as externally executed payments.
- **Transfer verification:** Existing server-required COT/exchange, IMF, and tax code checks are preserved. These are app-configured codes, not assertions of legal/regulatory clearance. Review their business purpose and customer support process. No fee-payment or code-purchase instructions have been added.
- **Idempotency:** The UI prevents concurrent submissions and blocks immediate retries after unknown/server-error outcomes. The ledger API still has no client idempotency key; production-grade retries across tabs/devices need a separate server-side design.
- **Identity documents:** The redesigned upgrade flow no longer uploads identity documents to the existing unsigned media endpoint. It sends a support enquiry only; no persisted upgrade case/approval state is invented. Provide a secured, access-controlled document pipeline before restoring identity-document collection. Previously uploaded documents still require a storage/access audit.
- **Avatar uploads:** Profile photos use the existing unsigned Cloudinary image service, with browser MIME/extension/2 MB checks. Server-enforced upload rules, authenticated upload signatures, and orphan-file cleanup need separate hardening. Do not use this service for identity documents.
- **Currency:** Amounts use the app's configured base currency/format, as before; the UI does not perform currency conversion. Supporting genuinely different per-account currencies requires an explicit account-currency contract and backend validation.
- **Authentication/session security:** Existing JS-readable cookie/session design is unchanged. User-scoped workspace data and drafts are cleared across session identities, and stale refresh responses are ignored. HttpOnly session migration, server-side revocation, rate limiting, and broader hardening remain separate backend work.
- **Notifications/support:** Intentional notification updates from `main` are preserved: paged list, detail view, entity links, bell preview, unread filters/counts, and live arrival toasts. The cheap unread count polls every 15 seconds only while the tab is visible; mark-read operations update locally only after server success. Support uses configured email/phone links; inconsistent auto-loaded third-party chat was removed from the customer layout.
- **Alerts:** Active app/admin alert helpers now use a single global Vue/Bootstrap toast host; the `sweetalert2` project dependency is removed. Dormant SweetAlert code remains in the supplied vendor theme bundle and unused template scripts; those compiled vendor assets were not hand-edited. No active customer screens load the old authentication template scripts.
- **Upstream notification schema:** The intentional `main` update adds notification `entity_type` / `entity_id` columns and an index. Existing databases need the migration documented in `db/README.md`; `DB_SYNC=true` does not alter existing tables. No database migration or historical debit/credit flip has been run against your real database by this task.
## Admin workspace follow-up

- **Financial idempotency:** UI review, in-flight guards and unknown-outcome warnings are implemented, but the credit/adjustment APIs still have no client operation key. Reconcile the recorded customer deposit and funding balance after any timeout before starting another operation. A reload cannot prove that an earlier request failed.
- **Currency truth:** Account `currencyId` may be a database identifier and transaction records do not carry a dependable currency snapshot. The admin UI avoids fabricated global-symbol totals, shows funding balances grouped by their labeled currency, and labels unresolved amounts as account units. Defaults do not convert balances. Associated credits now require matching funding/customer currencies on the server; nonzero funding balances cannot be relabeled to a different currency. No FX is performed.
- **Recent activity:** The existing user transaction endpoint returns a limited recent window by default. The admin user workspace labels it as recent activity; it is not a full ledger export or paginated historical search.
- **Sensitive controls:** Transfer codes remain an existing administrator capability, now masked and submitted only after confirmation. Server-side operation audit trails, stronger status validation (especially the exact semantics of `SUSPENDED`), two-person approval, and upload/storage policy need a separate security review. No authorization or ledger rules were weakened or rewritten for this UI task.
- **Legacy theme source:** Unmounted legacy sidebar/header templates remain for compatibility. Active admin routes no longer mount the two-sidebar shell or old prompt-based credit modal. Legacy credit/dropdown/profile entry components now delegate to the safer route/shared UI.

## Explicit funding operations follow-up

- **Client compatibility:** Signed funding `adjustment` payloads are rejected. Use `balanceChange: { direction: "credit" | "debit", amount: positiveNumber }`. The legacy positive-credit endpoint remains available, now with matching-currency validation for funding associations. See `docs/funding-operations.md` for contracts.
- **Correction accounting:** Customer corrections require a reason and write credit/withdrawal ledger entries. Administrative debits count under the existing outgoing aggregation and daily-limit accounting. A debit only changes the customer balance; funding associations are credit-only. Transaction reversals refund the sender once and never implicitly adjust a funding balance.
- **Audit and concurrency:** Funding-only changes still lack a separate durable operator history. Customer ledger reasons are not an immutable approval/audit system. SQLite concurrency tests verify no duplicate refunds, but a contending request may receive an error; PostgreSQL locking needs deployment-environment validation. Enums do not replace server idempotency keys or cross-device reconciliation.
